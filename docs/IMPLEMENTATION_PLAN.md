# MARSWALK — Implementation Plan

| Field          | Value                                                                    |
|----------------|--------------------------------------------------------------------------|
| Document       | IMPLEMENTATION_PLAN.md                                                   |
| Version        | 1.0                                                                      |
| Owner          | Orchestrator                                                             |
| Last updated   | 2026-11-11                                                               |
| Change control | Adding, removing or re-scoping a work package requires Orchestrator approval and a log entry in DEVELOPMENT_STATUS.md |

This plan breaks MARSWALK into work packages (WPs) in dependency order. Each WP has
a branch, deliverables, numbered steps, acceptance criteria and tests. Live progress
is tracked only in `DEVELOPMENT_STATUS.md`. Git rules are in `GIT_WORKFLOW.md`.

---

## 1. How to Use This Plan

1. Work on exactly one WP at a time, in the order of §5, unless the Status file says
   otherwise.
2. Before starting a WP, confirm every WP it depends on is `MERGED` (see
   `DEVELOPMENT_STATUS.md` §3 for status values).
3. Follow the WP's numbered steps. After each step, update the checkpoint in
   `DEVELOPMENT_STATUS.md` and commit (`GIT_WORKFLOW.md` §4).
4. A WP is done only when it meets the Definition of Done in `TESTING_STRATEGY.md` §9.
5. Code WPs (all except WP-00 and WP-05) may start only when `CODE_START_AUTHORISED`
   is `YES` in `DEVELOPMENT_STATUS.md`. The owner sets this after confirming the
   event rules.

#### WP-00 — Repository bootstrap
- **Branch:** none (initial commit on `main`, done by the owner)
- **Steps:**
  1. Create the repository folder and copy in the provided files.
  2. `git init`, set the default branch to `main`, make the initial commit.
  3. Create the `develop` branch from `main`.
  4. Create the GitHub repository, push `main` and `develop`, and apply the branch
     protection described in `GIT_WORKFLOW.md` §7.
- **Acceptance:** `main` and `develop` exist locally and on GitHub. Docs are present.
- **Tests:** none.

#### WP-05 — Data source selection (slug `data-sources`)
No application code. Allowed before the event.
- **Deliverables:** `docs/DATA_SOURCES.md`, `backend/data/manifests/data_sources.json`.
- **Steps:**
  1. Check the official challenge Resources tab (published 2026-11-13) and record its
     recommended sources in `DATA_SOURCES.md`.
  2. Confirm or change the region (open item O-1). Record the decision and reason.
  3. Identify specific products for: primary DTM (HiRISE), fallback DTM (CTX),
     optical (HiRISE orthoimage or CTX mosaic), thermal (THEMIS), geology (USGS
     global geologic map, SIM 3292), regional context (MOLA). P1 candidates: CRISM,
     MSL RAD, Curiosity Navcam/Mastcam.
  4. For each product, open its URL and confirm it resolves. Record product ID, URL,
     format, size, CRS information, resolution, coverage of the region and
     limitations. Never record an unverified URL.
  5. Define the region bounds so the primary DTM covers the planned traverse area.
  6. Write `data_sources.json` (schema: `API_CONTRACTS.md` §8.2).
- **Acceptance:** every P0 layer has a verified product, or a written reason it is
  unavailable. Total raw download size is stated.
- **Tests:** none (document review by the owner).
