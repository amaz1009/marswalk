## 1. Purpose

Tests prove that MARSWALK's numbers are correct, its safety rules cannot be bypassed,
and its interfaces match `API_CONTRACTS.md`. A test that was not run is never
reported as passed.

---

## 2. Test Levels and Tools

| Level | Scope | Tool | Location |
|-------|-------|------|----------|
| Unit | One function or module | pytest / Vitest | `backend/tests/unit/`, `frontend/tests/unit/` |
| Integration | API endpoints with the synthetic region | pytest + FastAPI `TestClient` | `backend/tests/integration/` |
| End-to-end (API) | Full journey through the API | pytest | `backend/tests/e2e/` |
| End-to-end (real data) | Smoke test on the processed real region | pytest, skipped with an explicit reason if data is absent | `backend/tests/e2e/` |
| Frontend | Store, API client, components | Vitest + Testing Library + jsdom | `frontend/tests/` |
| Manual | Clean install, demo walkthrough | Checklist in §7 | `docs/validation/TEST_REPORT.md` |

---

## 3. Commands (Windows PowerShell, from the repository root)

```powershell
# Backend (virtual environment created by scripts/setup.ps1)
.\backend\.venv\Scripts\Activate.ps1
cd backend
pytest                                  # all backend tests
pytest --cov=app --cov-report=term      # with coverage
pytest -m "not realdata"                # skip tests that need processed real data
cd ..

# Frontend
cd frontend
npm run test                            # Vitest
npm run typecheck
npm run build
cd ..

# Everything
.\scripts\test.ps1
```

Pytest markers: `realdata` (needs processed real data), `slow` (> 5 s).

---

## 4. Test Fixtures

- All unit and integration tests use **synthetic data generated by code** in
  `backend/tests/fixtures/`. No binary test rasters are committed.
- Generators include: tilted plane of a given slope, flat plane, ridge, wall of
  steep cells, enclosed basin, grid with `NaN` holes, checkerboard roughness pattern,
  and an asymmetric slope for return-leg tests.
- A synthetic region `test_synthetic` (config, catalog and rasters) is built in a
  temporary directory by `conftest.py`. Its datasets have data class `SAMPLE`.
- Synthetic fixtures are never shipped as demo data and never appear in the real
  catalog.
- Random grids use fixed seeds.

## 7. Clean-Environment Procedure (Windows)

1. Use a fresh clone in a new folder, with no existing `.venv` or `node_modules`.
2. Confirm `python --version` (3.11 or 3.12) and `node --version` (20 or newer).
3. Copy `.env.example` to `.env` without adding any API key.
4. Run `.\scripts\setup.ps1`. Record any error.
5. Run the data download and processing steps exactly as written in the README.
6. Run `.\scripts\test.ps1`. Record the results.
7. Run `.\scripts\dev.ps1`. Open the frontend, plan the demo route and generate the
   report.
8. Record every deviation from the README in `TEST_REPORT.md` and fix the README.

---

## 8. Reporting Rules

- Every WP records in `DEVELOPMENT_STATUS.md`: the exact test command, the number of
  tests passed, failed and skipped, and the commit hash.
- Skipped tests must state the reason.
- "Tested" means executed. A reasoned review without execution is recorded as
  "reviewed, not executed".
- Failing tests are never deleted or weakened to make a WP pass.

---

## 9. Definition of Done (every work package)

A WP is done only when all of the following are true:

1. All deliverables listed in `IMPLEMENTATION_PLAN.md` exist.
2. Interfaces match `API_CONTRACTS.md`. If an endpoint changed, `docs/openapi.json`
   is regenerated and `api.gen.ts` is regenerated in the frontend.
3. The WP's listed tests exist and pass, and the full existing suite still passes.
4. Error handling follows the contracts. No silent fallbacks.
5. No secrets, raw data or generated rasters are committed.
6. `ruff check` passes for backend changes; typecheck and build pass for frontend changes.
7. `DEVELOPMENT_STATUS.md` is updated with results and known limitations.
8. The WP branch is merged into `develop` following `GIT_WORKFLOW.md`.
